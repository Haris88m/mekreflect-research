# Publishing the research journal

The journal is a curated part of the dependency-free site build. It does not run a background research or publication service.

## Add an achieved milestone

Add a dated record in `journalEntries` in `research-journal.mjs`. Preserve a stable slug, entry number, work date, category, affected original task numbers, title, summary, evidence status, and source-linked body. Describe the claim before and after review, actual achievement, relevant revisions and execution context, remaining uncertainty and the next justified decision. Separate the date of historical work from its publication date.

Keep successful, negative, partial, disputed and unresolved findings where supported. Preserve corrections and earlier uncertainty. Identify reported evidence, source inspection, within-workflow checking, external review and independent runtime reproduction separately. Website build tests are publication checks, not scientific benchmarks. Counts of sources, assertions and tests never become independent-case counts or performance rates.

Use one of the existing categories, or add a category deliberately with a matching navigation anchor. Keep all 15 original research task IDs traceable to the full protocol and original workstream groups. New articles automatically enter category listings, the topic notebook, public journal JSON, the RSS feed and sitemap. Update the homepage's latest-note link when appropriate.

## Assess before release

Inspect exact source locations and revisions. Check rights, permitted summaries, privacy, sensitive identifiers and links. Store public methods artifacts through an explicit build entry and publish a content checksum when exact artifact identity matters. Do not publish raw private records, tokens, upstream incident logs or third-party text beyond permitted use. Unknown dependencies or rights block the affected execution or redistribution.

Run `npm run build` and `npm test`. Inspect desktop and mobile rendering, navigation, anchors, downloads and browser errors. Keep test submissions local or intercept them; never seed synthetic contact records into the production inbox. Publish only `dist-company`, whose contents must match the build manifest. Do not upload the repository, `private`, QA screenshots or development files.

Use the existing authorized deployment configuration for the existing `mekreflect` Pages project. Verify the actual production domain, canonical routes, download hashes, security headers, feeds, sitemap and existing pages after deployment. Record source commit, deployment ID and observed verification evidence outside the release tree.

## Scientific execution remains gated

Publishing a plan or conceptual graph does not admit an executable benchmark. Follow the full protocol's source/rights, dependency, safety, authority, resource and review gates. For the SDK candidate, retain the isolated parent/repair pair and one immutable behavioral oracle, pin the build environment, remove ambient credentials, disable provider/network effects and use synthetic effects. Update both D+ and S+ packet versions identically for the release-provenance correction and repeat parity checking before any representation comparison. Preserve the historical packet as historical.
